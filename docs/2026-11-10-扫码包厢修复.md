# 1.0.2 包厢识别与结算修复

用户从微信公众平台的通用体验码进入，页面未获得包厢场景参数。旧版允许继续结算，将空包厢提交给接口，返回“无效字段：room”。

## 修复后的行为

- 通用入口可以浏览和加餐；未识别包厢时，结算按钮显示“先扫码选包厢”。
- 首页包厢标签、购物车配送位置、确认订单配送位置均可发起扫码。使用微信 `uni.scanCode` 返回的 `path` 解析专属码，服务端核实后显示包厢号；通用体验码不能用作包厢码。
- 独立打开确认订单页也不会提交空包厢。确认下单前再次检查包厢码是否有效、包厢是否仍启用。
- App 再次进入时读取本次 `query.scene`，不把表示启动来源的数字 `scene` 当作包厢；连续扫码以最后一次为准，旧请求不能覆盖新包厢。
- H5 兼容 URL 普通查询参数中的 `scene`。H5 不支持原生扫描，明确提示使用微信扫一扫。

扫码返回字段依据：[uni.scanCode 官方文档](https://uniapp.dcloud.io/api/system/barcode.html)。

## 验证

- `npm test`：7 项通过，包含无包厢阻断、启动参数解析、无效码、网络失败重试和扫码请求乱序。
- 微信开发者工具：通用入口、直接进入结算、补扫码识别 V01、V01/V02 切换通过；真实服务生成的测试单 1010 可在管理员接口查看，未付款并已取消。
- 扫码相机结果通过开发者工具 API 模拟；后续包厢识别、登录、下单及取消使用真实线上服务。没有把模拟相机结果等同于手机摄像头实测。
- 浏览器使用新构建的静态资源和真实线上接口，验证通用入口/直接结算均不提交订单，以及普通 URL 参数识别 V01；运行错误为 0。
- H5、小程序构建成功；小程序 1.0.2 上传成功，大小 1,494,707 字节。
