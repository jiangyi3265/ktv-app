# 1.0.4 支付入口与 UI 验收

## 改动

- 删除 Checkout 中仿微信收银台的遮罩、零钱选项和第二次“确认支付”按钮。
- “确认并支付”创建订单后直接调用微信支付；订单列表及详情的“继续支付”使用原订单直接调用相同流程。
- 支付过程使用共享防重复锁；未支付时保留本次创建的订单供重试，服务端未确认付款时不展示成功页。已付款和关闭订单使用明确文案并禁用付款按钮。
- 旧 `pages/customer/payment?id=...` 地址保留为订单确认页面，兼容旧链接，不再展示仿微信面板。设计模式的模拟交易仍使用明确标注“不扣款”的演示提示，正式构建不会启用设计模式。
- 修复锁定包厢后橙色卡片文字过淡、长餐品名覆盖操作开关，增加原生详情页底部手势安全区留白。

## 验证范围

- 7 项领域与包厢识别测试、7 项设计模式交互流程、6 项回归检查通过。
- 使用隔离 MySQL 数据库中的待付款、待接单、制作中、配送中、已完成订单，检查 23 个页面在 320 / 390 / 430 三种宽度下的布局，共 69 组；无页面运行异常、图片加载失败或整页横向溢出。逐组复核截图中的文字、图片、间距、按钮和底部导航。
- 电脑后台订单、餐品、包厢与点餐码、食堂与权限、收支总账、支付接入、操作日志，在 1280 / 1440 两种宽度下检查，共 14 组，未发现页面异常或横向溢出。
- 微信开发者工具完成 23 个原生页面截图检查。最终独立构建目录再次核对确认订单、订单详情、接单、制作、配送、餐品编辑、账号权限页面的底部按钮均在手势安全区上方。
- 原生支付流程使用隔离测试数据和模拟微信回调：一次点击调用支付接口，快速重复点击及未付款重试只创建一笔订单，回调成功但服务端尚未确认时仍停留在订单确认页，服务端确认后才显示成功，历史订单继续付款保持原订单号。最终发布产物重新完成同一组支付检查。未进行实际扣款或向营业库写入模拟支付数据。
- 开发工具曾复用旧脚本配合新 WXML，导致空白页面或错误样式字段；最终使用独立构建目录重新加载并验证，上传该目录的产物。
